# 什么是数据库的事务？事务的四大特性（ACID）是什么？请简单解释每个特性。

**事务（Transaction）是数据库中的一组操作，要么全部成功，要么全部失败，具有原子性。事务通常用于保证多个操作的逻辑一致性。**

## A - 原子性 Atomicity
- 所有操作要么全部成功，要么全部失败
- 如果中途失败，则退回至事务开始之前的状态

## C - 一致性 Consistency
- 执行事务前后，数据必须从一个一致性状态转变为另一个一致性状态。比如转钱操作，A转钱到B，A钱少的数目一定要与B多的钱的数目一致。

## I - 隔离性 Isolation
- 并发事务之间互不干扰，每个事务在执行时应感觉不到其他事务的存在。
- 实际中通过隔离级别（Read Uncommitted、Read Committed、Repeatable Read、Serializable）实现。实际中通过隔离级别（读未提交、读已提交、可重复读、序列化）实现。

## D - 持久性 Durability
- 一旦事务提交，其结果就会永久保存在数据库中，即使系统崩溃也不会丢失。

# 讲一下事务的隔离级别，不同级别下会引发什么问题？

## 定义
事务隔离级别定义了多个事务并发执行时，一个事务对数据的修改在另一个事务何时可见，隔离级别越高，数据一致性越强，但并发性能越低。

## 四种标准隔离级别

| 隔离级别                     | 脏读  | 不可重复读 | 幻读  | 并发性 | 描述                         |
| ------------------------ | --- | ----- | --- | --- | -------------------------- |
| READ UNCOMMITTED  - 读未提交 | 可能  | 可能    | 可能  | 高   | 可以读到其他事务尚未提交的数据（脏读），最危险的操作 |
| READ COMMITTED - 读已提交    | 无   | 可能    | 可能  | 较高  | 只能读取已提交的数据（Oracle 默认）      |
| REPEATABLE READ - 可重复读   | 无   | 无     | 可能  | 中等  | 同一事务中多次读取结果一致（MySQL 默认）    |
| SERIALIZABLE - 可串行化的     | 无   | 无     | 无   | 低   | 强制事务串行执行，完全避免并发问题          |

## 不同级别引发的问题
- **脏读：Dirty Read**
	- 一个事务读到了另一个没有提交的事务
	- 举个例子：A查询操作，查询到了B还未交的事务的数据。
- **不可重复读：Non-Repeatable Read**
	- 一个事务前后两次读取同一行的数据，结果不一致（因此中间有别的事务进行了修改）
	- 举个例子：T1第一次查询记录结果R1=1，T2更改R1=2，T1再次查询R1，此时R1=2
- **幻读：Phantom Read**
	- 一个事务前后两次执行同样的查询，返回的“记录条数”不同
	- T1 读取所有 age > 20 的用户，T2 插入一个新的符合条件的用户，T1 再次查询时多了一行。

> 幻读与不可重复读之间的区别？

- 不可重复读： **同一行数据**在两次查询之间被其他事务修改或删除了。
- **幻读**：**查询结果集的记录条数发生了变化**，通常是因为有其他事务插入或删除了符合查询条件的新行或行。

# 什么是索引？为什么使用索引？常见的索引类型？

## 索引
索引是数据库为了加速数据检索而建立的数据结构，相当于图书的目录，可以大大提高查询效率。

## 为什么使用？

- 提高数据查询速度（最主要）
- 加速表之间的连接（JOIN）
- 加速排序操作（ORDER BY）
- 加快分组和聚合操作（GROUP BY）

>缺点：
> 	- 占用额外空间
> 	- 插入/更新/删除操作时需要维护索引，增加写开销

## 索引类型
- **B+Tree （最常用）**
	- InnoDB 的默认索引类型
	- 有序结构，适合范围查询（BETWEEN, >, <, LIKE 'xxx%'）
	- 叶子节点存储主键或行数据（聚簇索引）
- **Hash 索引**
	- 典型于 MEMORY 存储引擎
	- 只能做等值查询（=），不支持范围查询
	- 冲突处理机制复杂，较少用于复杂查询场景

# 索引什么时候会失效？

索引失效是指 SQL 查询**本来可以用索引，却最终没有使用索引**（比如使用了全表扫描）

## 1. `%前缀模糊查询` 导致索引失效
```sql
SELECT * FROM user WHERE name LIKE '%Tom';  -- 索引失效 ❌
SELECT * FROM user WHERE name LIKE 'Tom%';  -- 索引生效 ✅
```

## 2. 字段运算或函数操作
```sql
SELECT * FROM user WHERE YEAR(birth_date) = 1990;  -- 索引失效 ❌

-- 优化
SELECT * FROM user WHERE birth_date BETWEEN '1990-01-01' AND '1990-12-31';
```

## 3. 隐式类型转换
```sql
SELECT * FROM user WHERE phone = 1234567890;  -- 如果 phone 是 VARCHAR，索引失效 ❌
```

## 4. OR 连接多个字段且未全部加索引
```sql
--  如果只有 `name` 有索引而 `email` 没有，则整个 OR 语句无法使用索引。
SELECT * FROM user WHERE name = 'Tom' OR email = 'tom@example.com';  -- 部分索引失效 ❌
```

## 5. 使用不等于 (`!=`, `<>`) 和 `IS NOT NULL`
```sql
-- 不等查询或非空判断通常会导致全表扫描。
SELECT * FROM user WHERE age != 18;       -- 索引可能失效
SELECT * FROM user WHERE email IS NOT NULL; -- 索引可能失效
```

## 6. 在组合索引中没有遵循最左前缀规则
```sql
-- 有索引 (name, age)
SELECT * FROM user WHERE age = 18;   -- 索引失效 ❌（name 没有使用）

SELECT * FROM user WHERE name = 'Tom' AND age = 18;  -- 索引生效 ✅

```

## 7. 使用 `SELECT *` 且非覆盖索引


# 如何选择最优的 **联合索引顺序**
## 原则一：遵循最左前缀匹配原则（最关键）

只有从联合索引的**最左边字段开始，连续匹配**的条件才会用到索引。举个例子：
```sql
	-- 联合索引： (a, b, c)

	WHERE a = 1           -- ✅ 用上索引（a）
	WHERE a = 1 AND b = 2 -- ✅ 用上索引（a, b）
	WHERE b = 2 AND a = 1 -- ✅ 仍然用上（MySQL 会自动优化）
	WHERE b = 2           -- ❌ 不用索引（跳过了最左 a）

```

## 原则二：**将区分度高的列放在前面**

- **区分度（基数）**：唯一值越多，区分度越高。
- 例：手机号、用户ID 的区分度 > 性别（M/F）

## 原则三：根据查询条件优化顺序

- 优先考虑**查询中经常出现在 WHERE 条件中的字段**。
- 然后考虑排序字段（ORDER BY）、连接字段（JOIN）

## 原则四：考虑索引是否能**覆盖查询

所谓**覆盖索引**：查询的所有字段都在联合索引中，无需回表，提高性能。
```sql
	-- 联合索引: (name, age, email)
	
	SELECT name, age FROM user WHERE name = 'Tom' AND age = 20; -- ✅ 覆盖索引
	SELECT * FROM user WHERE name = 'Tom';                      -- ❌ 需要回表

```

# 如何查看一条SQL的执行计划？

- 最核心的方法是使用 `EXPLAIN` 关键字，直接在 SQL 语句前加上 `EXPLAIN` 即可。举个例子：`EXPLAIN SELECT * FROM users WHERE name = 'John' AND age > 30;`。
- 在 **MySQL 8.0.18 及更高版本**，强烈推荐使用 `EXPLAIN ANALYZE`。它不仅会输出执行计划的预估信息，还会**实际执行该查询**并输出真实的执行统计信息（如实际执行时间、实际读取的行数等），这比传统的 `EXPLAIN` 更加精确和有价值。

`EXPLAIN` 需要关注的字段：
-  `type` **(访问类型)**
	- **这是最重要的字段之一**，表示 MySQL 决定如何查找表中的行。性能从最优到最差大致为：
		- `system` > `const` > `eq_ref` > `ref` > `fulltext` > `ref_or_null` > `index_merge` > `unique_subquery` > `index_subquery` > `range` > `index` > `ALL`
- `key`**(实际使用的索引)**
	- 显示 MySQL **实际决定使用的索引**。如果这一列为 `NULL`，则表示没有使用索引，需要高度警惕（除非表很小）。
-  **`rows` (预估扫描行数)**
	- 表示 MySQL **预估**为了找到目标行需要扫描的行数。**这个值越小越好**。
-  **`Extra` (额外信息)：
	- **包含了关于 MySQL **如何解析查询**的额外重要信息。有几个值尤其需要关注：
		- **`Using filesort`：** **红色警报！** 表示 MySQL 无法利用索引完成排序，必须额外进行排序操作（可能在内存或磁盘）
		- **`Using temporary`：** **红色警报！** 表示 MySQL 需要创建一张临时表来存储中间结果（常见于 `GROUP BY`, `DISTINCT`, `UNION`, 子查询或一些 `ORDER BY`）。
		- **`Using index`：** **好消息！** 表示查询使用了**覆盖索引**，即所需数据列都包含在索引中，**无需回表查询数据行**。这通常是最快的数据访问方式之一。
		- `Using where`： 表示存储引擎返回的行需要在 Server 层再进行过滤（WHERE 子句中的条件并非所有都能被索引完全覆盖）。
		- `Select tables optimized away` / `Using index for group-by`： 通常是优化的好现象。

# 乐观锁、悲观锁

在多线程/分布式环境下，多个事务同时访问数据库同一资源时，会导致**数据不一致**问题。锁机制通过控制并发访问，解决**丢失更新**等并发冲突问题。

## 悲观锁
假设别人一定会修改数据，因此在操作前**先加锁**，防止并发问题。

>原理：

- 依赖数据库的 行级锁 机制
- 事务开始前显示加锁，事务结束后释放锁（加锁后其他事务无法读、无法写）
- 通过`SELECT ... FOR UPDATE`实现

## 乐观锁
假设别人一般**不会修改数据**，操作时**不加锁**，在提交时通过版本等机制验证是否被修改。

> 原理

- 添加**版本**字段（如 `version`）
- 更新时校验版本是否变化 `UPDATE ... SET version=新值 WHERE id=ID AND version=旧值`
- 根据影响行数判断是否成功（0行=有冲突）

>举个例子：

```java
// 数据库表添加version字段
public void deductBalance(int userId, int amount) {
    int retryCount = 0;
    while (retryCount < MAX_RETRY) {
        // 1. 查询当前数据和版本
        Account acc = accountDao.selectById(userId);  // 包含id,balance,version
        
        // 2. 执行业务计算
        int newBalance = acc.getBalance() - amount;
        
        // 3. 尝试更新（带版本校验）
        int rows = accountDao.update(
            "UPDATE accounts SET balance=?, version=version+1 " +
            "WHERE id=? AND version=?", 
            newBalance, userId, acc.getVersion()
        );
        
        if (rows > 0) {  // 更新成功
            return;
        }
        retryCount++;  // 版本冲突，重试
    }
    throw new ConcurrentUpdateException("更新失败，请重试");
}
```

# 讲一下MySQL中三大日志的工作流程

`MySQL` 中的三大日志是：
- `undo log` **回滚日志**， InnoDB 逻辑日志，核心保证事务的**原子性**和实现 **MVCC**。记录数据修改前的旧版本，用于事务**回滚**和提供**一致性读**。
- `redo log` **重做日志**，  InnoDB 物理逻辑日志，核心保证事务的**持久性**。采用 **WAL 机制**，确保已提交事务的修改在崩溃后能**重做**恢复。顺序写，速度快。
- `binlog` **二进制日志**，逻辑日志，核心用于**主从复制**和**时间点恢复**。记录所有**数据更改语句**。

此处采用一个案例的形式介绍一下三大日志的工作流程，首先先给他们代入一个角色：
- **数据库管家 (InnoDB 存储引擎)：** 负责具体的数据存取和事务管理。
- **账房先生 (磁盘上的数据文件 `.ibd`)：** 保管着最终、持久化的商品库存、订单等数据。
- **速记员 (redo log)：** 拿着两个快速轮换的笔记本 (`ib_logfile0`, `ib_logfile1`)，**只记录管家对数据页做了什么改动**（比如：订单表第 5 页，第 3 行，库存字段从 100 改成 99）。他的速度很快。
- **时光回溯员 (undo log)：** 手里有一本神奇的“时光相册”（回滚段）。每当管家要修改数据前，他**立刻拍一张修改前的快照**存起来（比如：库存原来是 100）。这本相册也用于给其他正在看数据的人展示过去某个时刻的样子（MVCC）。
- **广播员 (binlog)：** 拿着一个大喇叭和一个永不消磁的录音带。他**用人类语言记录管家执行的每一个重要的数据变更命令**（比如：`UPDATE inventory SET stock = stock - 1 WHERE item_id = 123;` `INSERT INTO orders ...;`）。他的录音带要发送给各个分店（从库）让他们照着做。

介绍完几个角色以及他们所具备的功能之后我们来看一个**正常的下单流程**：
1. 用户点击下单。”我要买苹果16手机“，此时会开启一个数据库事务。
2. **时光回溯员行动 (undo log)**：管家（**`innodb` 引擎**）准备扣减库存（比如把 100 改成 99）.
	1. **时光回溯员(undo log)** 立刻拍下库存 100 的快照，存进“时光相册”(undo log)，事务回滚时就参照此快照。
3. 管家（**`innodb` 引擎**）修改内存：管家在**内存**中找到库存数据页，把库存从 100 改成 99。此时内存中的数据与数据库磁盘中的数据不一致了。
4. **速记员记录动作：**
	1. 管家（**`innodb` 引擎**）会告诉**速记员（`undo log`）**: "你记录一下，库存数据页 XX，位置 YY，从 100 改成 99"
	2. 速记员记录管家的指令到笔记本上（redo log buffer），**为持久化做准备**。
5. **广播员记 (`binlog`)录命令**：管家告诉广播员：“记下来：我执行了 `UPDATE inventory SET stock = stock - 1 WHERE item_id = 123;`”。广播员把这个 SQL 语句（或等效的行变更逻辑）写进他的**录音缓冲区** (binlog cache)。
6. **两阶段提交 (2PC) - Prepare 阶段 (管家和速记员确认)：**
	1. 管家（**`innodb` 引擎**）问速记员（`undo log`），”我准备提交数据了，你那边关于库存修改的记录准备好了吗？“
	2. 速记员（`undo log`）回答：”准备好了“。然后**立刻把他笔记本上关于这个事务的所有改动（包括‘准备提交’的标记），工工整整地抄写到另一个更永久的、不会丢的账本上（`fsync` redo log 到磁盘）**，并标记这个事务的状态为 `PREPARE`。 **关键点：此时改动已在 redo log 持久化！**
7. **两阶段提交 (2PC) - Write Binlog (广播员录音)：**
	1.  管家（**`innodb` 引擎**） 对广播员 (`binlog`)说：”一切工作准备就绪，你现在**正式把关于这个订单的所有变更命令（UPDATE, INSERT...）录到你的永久录音带（ `binlog记录 -》 磁盘，注意！！此处并不是真正的修改账房中的数据`）**“
8. **两阶段提交 (2PC) - Commit 阶段 (管家最终确认)：**
	1. 管家（`innodb 引擎`）收到广播员（`binlog`）“录音完成”的确认后，**再次告诉速记员：“正式提交！”。**
	2. 速记员（redo log）在之前持久化的记录后面，**飞快地追加写上 `COMMIT` 标记 (`fsync` 包含 COMMIT 的 redo log)**，并将事务状态改为 `COMMITTED`。
9. **通知用户** ： 管家反馈，下单成功
10. **账房先生慢悠悠更新 (刷脏)：**
	1. 内存里那个被改成 99 的库存数据页（脏页）**还没写到账房先生（磁盘）那里**！
	2. 管家会找个**后台空闲时间**，或者当速记员的笔记本快写满时，才把内存中累积的脏页（库存改、订单新增等）**批量**、**安静地**同步给动作慢的账房先生（写入磁盘数据文件 `.ibd`）。**因为速记员已经记录了所有改动，即使此时崩溃，也能恢复，所以这里可以延迟处理，提高性能。**

> 正常流程总结

1. 用户提交 `sql`，数据库开启事务
2. `undolog` 拍下处理前的快照
3. `innodb` 读取数据到内存中，在内存中修改数据
4. `undolog` 记录 `innodb` 的操作日志，此时的日志记录在 `undolog buffer` 中
5. `binlog` 记录 `innodb` 进行的 `sql`（只记录修改语句，`del`、`update`、`inster`） 语句，此时也是记录在缓冲区
6. `innodb` 向 `undolog` 确认是否记录成功。`undolog` 回复，并将事务的所有改动写到 磁盘上。`undolog buffer` -> 磁盘。并将事务状态改为 `prepare`
7. `binlog` 记录。`binlog` 将缓冲区内容记录到磁盘中。记录后并通知 `innodb`
8. `innodb` 收到通知后，正式提交事务，并将状态改为 `commited`
9. 用户收到结果反馈
10. 数据库持久化数据。内存 -》磁盘

# Binlog
## 是什么？

Binlog（Binary log） 二进制日志文件。

## 能做什么？

- **核心作用：记录所有对数据库结构或内容进行更改的 `数据操作语句` (DDL 和 DML，如 `CREATE`, `ALTER`, `INSERT`, `UPDATE`, `DELETE`)，以逻辑的、语句或行格式的形式存储。它不记录 `SELECT` 或不修改数据的语句。**
- 关键用途：
	- **主从复制**：这是 `binlog` **最核心**的作用。主库 (`Master`) 将 `binlog` 发送给从库 (`Slave`)，从库重放 (`replay`) 这些日志事件，从而保持与主库的数据一致性，实现数据冗余、读写分离、负载均衡和高可用基础。
	- **时间点恢复**
	- **审计**
-
